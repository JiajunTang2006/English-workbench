**R1：撤销应重新计算“有效事件集合”，不能只把原奖励减掉。**

位置：`backend/app/services/growth/rules.py:282–307`。

同一天完成三次任务，现有每日最多两次规则得到 `[2, 2, 0]`。撤销第一条，当前重算结果是 `[2, 2, 0, -2]`，合计 **2**；剩下两条有效任务本应得到 **4**。代码在处理后置撤销时释放额度，但没有重新处理先前因封顶得到零分的有效事件。

另外，连续三周周目标奖励 `[2, 2, 3]`，撤销第一周后仍累计 **5**，而剩下只有连续两周，应为 **4**；`goal_weeks` 没有排除已撤销目标。

建议：先确定撤销关系和有效事件，再对有效事件按稳定顺序计算日/周封顶及连续周数。审计账本保留原事件和更正关系；若保留财务式冲正流水，必须同时记录其他事件的奖励调整，保证投影与流水净额一致。不要简单删原记录，也不要对零分事件无条件减少“已奖励次数”。

验收：三任务撤销、周封顶释放、撤销零分事件、撤销连续周中间一周、补录历史日期、重复撤销的结果一致且可重放。

**R2：自动考试奖励需要来源修订与对账。**

位置：`backend/app/services/growth/exam_events.py:103–138`。

幂等键只有考试与学生。复现两次考试 60 → 70，第二次进步奖励为 2；将第二次成绩纠正到 60 后重新同步，仍保留进步奖励 **2**。再撤销该成长事件并同步，返回 `created=0`，因为已撤销事件的旧键仍在集合中。因此文件说明里的“撤销后重新同步”实际上不能修复奖励。

建议区分“同一来源的同一修订重试”与“来源真的修改”：记录成绩/出勤/满分/可比组的修订号；修订变化时追加更正或替代关系，重算该学生受影响的后续可比测评奖励。改成缺考、删除或归档考试也要对账。历史低分被更正后，后续基线不能仍用旧值。

还应统一同步入口：目前自动成长同步挂在 workspace 保存路径，应检查学校 API 同步、成绩审核确认、改分和删除等所有事实写入入口。避免依赖一次无关的页面保存才产生奖励。

验收：重复同步不重复奖励；60→70 改为60→60后净奖励正确；缺考修订撤回奖励；撤销与合法更正可恢复；补入早期考试会修正后续基线。

**R3：分支查询必须复用正式试卷版本与分析资格口径。**

位置：`backend/app/services/growth/performance.py:81–94`。

查询直接连小分、题目与考试，没有限定该考试当前选中的 confirmed 版本。复现中，正式题目算出的阅读表现为 **0.6**，只添加一条新草稿零分题，正式成绩完全不动，成长树阅读表现便变成 **0.4**。旧版本保留小分也存在同样风险。

建议复用 `services/paper_versions.py` 的最新 confirmed 选择规则；过滤不参与正式分析的记录，并统一缺考、缺分与证据质量口径。不要另写一套“所有 confirmed 都算”的过滤，因为同一考试可能保留多个已确认版本。

验收：草稿增删不影响正式树；替换确认版本后只计新有效版本；无正式版本显示待确认；被排除的小分不进入正式能力值。

**R4：按学期隔离请求和缓存。**

位置：`workbench-assets/workbench-growth.js:47–51、105–123`。

模拟学期 1 的请求尚未返回时切到学期 2：`growthInvalidate()` 不清除旧数据/加载状态，新请求被 `growthLoading` 拦住；旧响应随后落到 `growthData` 并设置 `growthLoaded=true`。实际复现得到“当前学期 2、数据 term_id=1、只发过学期 1 请求”。现有前端测试覆盖的是上一次加载已经结束后的切换。

建议：使用请求序号和捕获的 `term_id` 校验响应；切换范围递增序号并清空旧视图，旧响应直接丢弃；按范围维护加载状态，允许发起新学期请求。详情缓存以 `(term_id, student_id)` 为键；补录弹窗固定并验证打开时的学期，切学期关闭旧弹窗。

验收：延迟/失败/乱序响应下连续切换学期，卡片、统计、详情和写入目标始终一致。

**R5：读取不应删除、重建整份奖励表。**

位置：`service.py:65–68` → `snapshots.py:26` → `events.py:136–157`。

森林读取逐个学生调用 `build_snapshot`，内部删除该生所有奖励并重新插入。在只有两名学生的临时样例中，一次读取产生 **19 条 SQL，其中 2 次 DELETE、4 次 INSERT、1 次 UPDATE**。数字只是该样例的执行证据，不是生产性能基准。

路由 GET 的 Session 关闭时没有提交这些改动，写入最终回滚；但中间仍进入写事务，重复计算和 SQLite 锁竞争风险实际存在。画像摘要同样触发重建，可能抵消前面针对 TeachMate 响应速度的优化。

建议：事件/成绩提交事务更新受影响学生的投影与失效标记；GET 批量读取已经提交的快照。必要的后台重建使用独立事务，并保留一致性修订号。每周值可由已存奖励按当前业务周查询，不必重建所有奖励。

验收：预热后的 GET 无 INSERT/UPDATE/DELETE；模拟实际班级规模测量 p50/p95；并行读取与补录不出现锁错误。不要通过在 GET 末尾加 commit 来“修好缓存”，那仍然把全量重算留在读取路径上。

**R6：画像引用应覆盖它实际引用的全部事实。**

位置：`snapshots.py:69–72`、`events.py:180–190`、`summary.py:161–183`。

当前 `source_revision` 只哈希活动事件和奖励。上述阅读表现 0.6→0.4 的复现中，修订号完全相同。题目成绩、标签、有效版本、规则阈值或本周窗口改变，都可能不触发成长引用过期；这里特指成长引用状态，并不等于其他报告过期机制一定全部失效。

建议拆为活动奖励修订、学业证据修订、规则版本与统计窗口，再把实际引用的部分组合为画像引用指纹。`growth_profile_status` 同时校验规则版本。画像若引用能力分支，应冻结数值、样本数、日期跨度、比较口径及来源 ID；目前 `summary.py` 只传递维度 status，不能支持模型描述具体趋势。

另外，摘要只计入拿到正奖励的完成/订正事件：被封顶不等于未完成。事实次数应统计全部有效事件，奖励次数另列，避免学生做得越多、事实反而被限额截断。

**R7、R8：补录幂等与班级统计。**

- `workbench-growth.js:348–364`：每次点击生成新的随机 request_id，且没有提交中禁用。快速连点可以把一次活动记成两次并奖励两次。弹窗/操作创建时生成稳定 ID，同一次提交重试复用；提交中禁用。以后任务账本接入后，再按任务或活动实例做业务去重，不要只按学生和日期去重，以免吞掉两次真实任务。
- `workbench-growth.js:177–182`：卡片按班级过滤，顶部直接用全学期 `growthData.summary`。改为后端按 class_id 同范围返回，或对已加载的完整筛选结果重新汇总；不要以分页中的可见卡片计算全班统计。

**三、规则本身如何改进**

**1. 保留三段式，但纠正当前解释。**

“基础分 + 进步分 + 里程碑分，受日/周上限约束”可以继续使用。基础分奖励有效参与，进步分奖励可核对的个人进步，里程碑奖励持续达成。成长营养仍是产品激励，不能解释为英语能力或学生优劣。

当前公式 `floor((本次得分率−基线)/0.05)` 对相同百分点提升一视同仁，并没有额外的“低基线补偿”。现有测试把35%→45%与95%→98%相比，分别是10和3个百分点；测试注释却称同样提升10个百分点，不能证明低基础学生在相同提升下更易得分。建议改成准确解释“与自己比较”，并增加35→45与75→85同奖的测试。

不要为了补偿低分直接除以 `(1−基线)`；这会在高基线附近放大微小波动。高分学生缺少提升空间的问题，可以用“连续达成适合自己的目标/复测保持”表彰解决，且与进步奖励去重，不必硬改为绝对高分多给营养。

**2. 先建立可比组，再算进步。**

目前 `_previous_rate` 实际选的是上一次有效考试，不限定能力分支、测评类型、量表或难度。把默写60%和综合测评70%相减，不能推出能力提高10个百分点。`performance.py` 虽保存 exam_type 到元组，随后也没有按它分组。

建议使用 `comparison_group_id`，由教师/明确规则把相同能力、测评形式、评分量表版本及已确认可比难度的测评归组。没有可比基线时只给参加基础分，进步分标为“依据不足”。同一个 exam_type 本身不足以证明难度可比。

同一可比分支内，先在每场测评聚合有效得分/有效满分，再做时间平滑。现在直接平均每一道题的得分率：1分题得1分、9分题得0分，会得到50%，而该分支总得分率是10%。若产品确实需要等权题目指标，必须改名并解释权重，不能把它称为总得分率。

**3. 避免反复奖励同一段回升。**

只比较上一次且退步不扣，会让60→70→60→70得到两次满额进步奖；60→70→70→70只有一次，虽然起终点相同。不能仅凭这一序列认定学生有意刷分，但激励结构确实奖励了波动。

建议把展示基线与奖励基线分开：近期展示可用最近三次可比测评中位数或现有平滑值；进步奖励采用“已确认、已奖励到的进步里程碑”，同一档位不重复发奖，新的档位经过另一日期复测后确认。初始基线不足时先积累证据；来源更正时修正已确认档位。不要直接拿某一次偶然最高分作为永久门槛。

这是一项候选产品规则，不是已经由本校数据证明的最优方案。先用历史序列模拟：稳定高分、稳定低分、持续进步、偶发低分、缺考、改分，观察是否符合教师预期。

**4. 连续周奖励按教学周，而非自然周断档。**

目前按相邻自然周计算，节假日、停课和认可请假也会打断。建议给学期维护教学周和豁免状态：非教学周跳过，认可缺席暂停，不自动发奖；真实未达成才中断。撤销周目标后，后续连续周奖励必须重算。

更温和的候选是“最近四个有效教学周达成三周”，但应作为新规则版本试点，不在学期中途悄悄替换。

**5. 成长阈值需要活动频率支撑。**

当前阶段为0/30/80/160/270/400/560，周上限40。560分最快也需14个计分周；按注释假设每周30分，约18.7周。若学生只有每天一次任务、每周五天，则每周10分，需要56周；这只是说明“发芽一周、学期成树”取决于真实记录频率。

建议先试点2–4个教学周，统计有效活动机会、实际记录覆盖、周积分分布、封顶比例与教师补录耗时，再决定阈值。不要把“老师没时间录”误判成“学生没有成长”。阈值以学期规则版本冻结；当前默认 rule code 全局选择、奖励重建覆盖旧值的机制，还需要补上学期与规则版本绑定。

保留日10/周40作为暂定安全上限可以，但不建议现阶段依据几条样例就宣布它最合理。先解决重复计分、机会差异和记录负担，调上限才有意义。

**四、模型选择与工程落地顺序**

树的阶段是根据已定义激励规则展示的状态，不是等待模型发现的标签。用 Softmax 学习种子/发芽/开花，再回归成长值，会引入两套不容易一致的尺度；没有外部目标标签时，通常只是重新拟合自己设定的规则。多分类逻辑回归本身是监督分类方法，参见 [scikit-learn 官方文档](https://scikit-learn.org/stable/modules/generated/sklearn.linear_model.LogisticRegression.html)。这里“不采用它”的判断来自本项目需求，并非文档对教育产品的结论。

建议当前维持：**营养用确定性规则，分支用可比测评得分率与时间平滑，语言模型只组织有证据的画像文字。** 现有 `M_t=0.3x_t+0.7M_(t−1)` 符合指数加权移动平均的形式，可用于平滑观察值；它本身不等于知识掌握概率，也不会自动证明稳定进步。方法形式参见 [NIST EWMA 说明](https://www.itl.nist.gov/div898/handbook/pmc/section3/pmc324.htm)，0.3在本项目中仍是待验证初值。

以后若要预测“下一次独立测评表现”，再单独训练预测模型，用按时间留出的未来测评验证；预测结果不直接修改已发营养或历史树阶段。现阶段首要缺口是有效、可比、可追溯的事实，而不是模型复杂度。

推荐修改顺序：

1. **事实与积分正确性**：R1–R3、成绩来源修订对账；补上对应回归测试。
2. **范围与交互正确性**：R4、R7、R8；覆盖请求乱序和连点重试。
3. **读写与画像一致性**：R5、R6；快照异步/事务更新、完整引用修订、事实次数与奖励次数分离。
4. **教学规则试点**：可比组、进步档位复测、教学周、阈值模拟；学期规则版本冻结。

不需要立即拆微服务。保持当前模块化后端，统一事实写入入口，用事务内投影或持久化任务处理受影响学生，已经足以明显改善一致性与响应速度。
