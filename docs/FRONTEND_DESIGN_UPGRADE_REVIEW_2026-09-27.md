# 前端改造评审与实施建议

日期：2026-09-27。评审对象：`docs/FRONTEND_DESIGN_UPGRADE_PLAN_2026-09-27.md`。

评审依据：当前源码与样式加载顺序、近期学生画像布局问题，以及文末的公开规范。本次是静态代码评审，没有重新进行浏览器视觉验收或性能测量；“代码已有”不等于每个场景都已正确接入。本次只新增评审文档，不实施新一轮界面改造。

## 1. 总体判断

有实施价值，但不建议照原方案整体执行。它适合作为灵感清单，还不是可以直接排期的实施方案：现状判断有遗漏，部分建议重复已有能力，部分视觉建议会改变教学信息的含义，且“不动 shell”与改侧栏、顶栏、全局滚动存在范围冲突。

建议把目标改成：**保留暖纸视觉，减少操作和阅读负担，让数据范围、任务状态、结果来源更清楚；用少量动效表达真实变化。**

约束：只针对 PC；保留当前原生 JS 与 ECharts；不因参考项目使用 React/Vue 而引入框架；不为了视觉一致改动计分、画像确认和数据写入语义。侧栏与顶栏如要调整，必须在实施方案中明确列为范围，不能同时写“shell 保持原样”。

## 3. 建议删除、延后或缩小的内容

| 原建议 | 处理 | 原因与替代方案 |
|---|---|---|
| 全部页面按屏宽自动变三栏 | 删除统一规则 | 大屏表格需要列宽，聊天需要可读行宽。只在有真实详情或成果时显示辅助区，不创建空洞察侧栏 |
| PC 小于 1280px 自动单栏加抽屉 | 删除统一规则 | 窗口变窄不等于移动端。允许表格横向滚动、辅助区收起；按具体组件的最低可用宽度处理 |
| 顶栏增加面包屑、标签页工作区、命令面板 | 延后 | 三种导航同时加入会增加复杂度。优先保留筛选、滚动位置和未保存草稿；有跨模块高频搜索需求后再做一个统一搜索入口 |
| 所有表格去斑马纹，行 hover 抬升 | 删除统一规则 | 密集录分表可以保留很淡的条纹；行不位移，hover 只变底色。固定姓名列、键盘连续录入更有价值 |
| 每个 KPI 都有滚动数字、delta、sparkline | 缩小 | 首批只优化 3–4 个真正影响教师决策的指标，详情放到点击后的视图 |
| KPI 涨红跌绿 | 替换 | 不套用证券配色。按“改善/需关注/中性”表达；名次从 20 到 15 应写“进步 5 名”，缺考率上升不应被当作改善 |
| 无数据绝不用 0 | 改写 | 缺失显示“—/待录入”；真实 0 分、0 条待办必须保留。失败、加载中、样本不足分别展示 |
| 班级营养榜作为默认横向对比 | 不纳入首批 | 当前代码明确提示不同教师标准下不可直接比较（`workbench-growth.js:46`）。优先展示本人阶段、本周记录与待订正；即使同口径也不能称为能力榜 |
| 工具过程展示“逐步推理” | 改写 | 展示真实工具动作、数据范围、执行结果、错误及证据摘要。不要伪造思考过程，不把思考字数作为质量指标 |
| 流式回复人为模拟打字节奏 | 删除 | 按真实到达内容显示，可合并渲染以避免闪动，但不增加人为等待 |
| 全局批量动作都加撤销 Toast | 缩小并移到 P1 | 只有存在可靠逆向操作的动作才提供撤销。已持久化数据不能靠恢复前端快照实现撤销 |
| 账本表格全部改时间轴 | 不做整体替换 | 教师核对时间、事由、分值、状态时表格更方便。保留账本表格，单条详情可用时间轴表达更正关系 |
| 班级、学期统一做分段滑块 | 缩小 | 2–4 个固定选项可用分段控件；班级较多时保留下拉或搜索，否则滑块只是增加横向占用 |
| 全站模态从触发点缩放、倾斜卡片、光束边框、3D 按钮 | 删除 | 对当前教学任务收益小，且会增加定位感变化；保留轻量按压、焦点和必要的展开反馈 |
| 暗色模式 | 延后 | 当前暖纸主题尚有多层覆盖，先稳定一套主题，再评估实际需求与图表/导出的配套成本 |
| 全局 tabular-nums | 缩小 | 只用于成绩、日期、百分比和 KPI 等数字区域，正文和标题保留原排版 |
| 全站 ECharts 同时开启 brush/dataZoom | 删除统一规则 | 长时间序列再加缩放；确有多图联动筛选任务才加 brush；雷达图不套用这套交互 |
| 按 GitHub 星数选参考 | 删除星数排名 | 本次未重验仓库星数与活跃度。参考项目应对应一个明确问题，不能把仓库清单当成功能需求 |

## 4. 推荐实施清单

### P0：先让现有页面稳定、状态明确

**A. 样式归属和资源发布**

- 保留 `--wp-*` 作为当前主题原语，`--md-*` 与 `--tm-*` 继续作为模块语义别名。
- 每个组件确定一个结构样式归属文件；主题文件负责颜色、文字与阴影，不再重复控制学生弹窗宽度等结构属性。
- 从学生详情、成绩表、TeachMate 三个高频区域逐个清理覆盖，避免一次性清空几千行 CSS。
- 复用现有动效令牌，区分颜色、阴影、尺寸等 token 类型，避免同名变量被赋予不同类型的值。
- 不直接把新增规则包进 `@layer` 当作解决方案：未分层的普通规则会优先于分层的普通规则；必须连同现有层叠关系设计迁移。[MDN 层叠说明](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Cascade/Introduction)
- 将资源指纹、源码与包内资源一致性检查纳入构建。正式发布从同一源码构建前后端；直接替换旧包静态资源只能作为临时修补，需要兼容性核对。

验收：能指出每个重点组件的最终样式来源；刷新和重新打开同一构建结果一致；不再靠重复追加覆盖规则解决问题。

**B. 学生画像与 PC 空间使用**

- 落实已确认的要求：右侧能力图使用稳定宽高，图形等比占据图表区；左侧内容增加不能拉伸或挤动右侧。
- 左侧内容很长时，使用受限的左侧内容滚动区域；普通长度按内容收口，不为了对齐制造大块空白。明确区分“左侧文字增长”和“用户主动滚动整个详情”。
- 学生详情不因打开画像、确认建议或重新加载数据而自动跳回顶部。
- 页面区分三种骨架：数据录入页、学生详情页、Agent 工作页。不要所有页面都强行套 KPI 条加三栏。

验收：建议在 1280、1440、1920 CSS 像素宽度及浏览器缩放 125% 下检查；同一窗口下，左侧由短摘要变成长摘要时右侧位置和尺寸不变；图表标签不裁切。

**C. 数据与任务状态**

- 区分首次未建数据、筛选无结果、加载中、加载失败、资料不足五种情况。
- 空状态给一个直接下一步，例如“导入成绩”“清除筛选”“重新加载”“补充试卷”；不每个状态都放大型插画。
- 将现有骨架接入首次异步加载；刷新已有页面时保留已有内容和筛选，加轻量更新状态，避免整页闪空。
- 高频控件满足键盘可达、可见焦点、弹层关闭后焦点返回；状态变化按任务阶段播报，不逐字播报。

验收：失败不显示成“暂无数据”；零分不显示成缺失；快速切换班级和学科不出现前一个范围的数据；输入过程中异步刷新不夺焦点。

### P1：让教学操作更省事、结果更好用

**D. 成绩表与 KPI**

- 成绩表优先固定姓名/学号列与表头，保留连续录入、未保存提示、异常单元格说明和批量操作反馈；已有能力先核对，再补缺口。
- 批量选择明确“已选人数”和范围；切换班级或学期后清空选择或明确提示，不能悄悄操作隐藏学生。
- 首批指标建议围绕均分、达标率、待跟进人数、数据覆盖率；指标必须能解释计算范围并有可追溯入口。
- 跨考试对比需同时检查学科、学生群体、满分和测评可比性。即使换算成得分率，也不能默认难度相同；条件不足时不输出“进步/退步”结论。
- 变化显示文字和符号，不只靠颜色；比例变化区分“百分点”和“百分比”。[W3C 颜色使用说明](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)

验收：当前班级、学期和样本数清楚；点击指标能找到组成记录；真实零值、缺考和缺失均能区分。

**E. TeachMate 对话与教学成果**

- 复用现有过程区，将教师主视图收敛为“读取资料 → 核对范围 → 分析 → 整理材料”等有真实事件支撑的状态；只有状态发生变化时更新。
- 统一普通回复和结构报告的复制入口；结构报告提供“复制结论”，材料提供对应导出，技术诊断信息放在次级菜单。
- 重试必须说明重试的是当前任务还是失败学生，不能混成一个不明确的按钮；有写入行为的任务沿用现有确认与防重复机制。
- 已有“调整教学包”等动作继续使用；缺少时补充最多 2–3 个相关下一步，不每条消息都堆建议。
- 后续动作绑定对应会话、报告与数据范围，避免用户切换考试后对旧报告执行了新范围的操作。
- 证据入口尽可能定位到具体考试、题型或记录；无法定位时明确说明，不能只弹一段原始 JSON。
- 保留用户阅读历史时的滚动位置；需要时提供“有新内容/回到最新”按钮。优先增量更新局部，减少全量渲染导致的闪动、选择丢失和折叠状态重置。

验收：长回复和工具更新期间不打断选中文字；停止、失败、重试状态清楚；导出的学生练习单与教师答案分开；后续动作使用正确的报告上下文。

**F. 有边界的撤销**

- 从成长补录单条记录开始，Toast 可提供“撤销”，但调用现有追加撤销事件的接口，不删除原记录（`workbench-growth.js:584`、`backend/app/routers/growth.py:103`）。
- 点击后显示处理中与结果；遇到重复点击、范围切换或服务失败，不宣称撤销成功。
- 通知消失后仍能从账本撤销；批量补录若无整批逆向契约，不用前端多次请求伪装成原子撤销。
- 编辑成绩、导入文件等操作各自评估逆向能力，不能将“撤销 Toast”当作无后端依赖的视觉组件。

验收：重新加载后状态一致，原记录仍可追溯，失败不会出现界面已回退而数据库未回退。

### P2：少量动效与成长体验

- 保留现有七阶段树；仅在当前操作确实造成阶段变化时提示一次，不在每次刷新或全班批量渲染时庆祝。
- 更值得增加的是“哪些学生本周缺少记录”“哪些订正待跟进”入口，而不是默认营养排行榜。
- 少量 KPI 可在真实值变化时短暂过渡，初次打开直接显示最终值；轮询相同数据不重播。
- 表格行只变底色，按钮有轻量按压，展开区平滑打开；不使用循环光晕和悬浮卡片位移。
- 减少动态效果模式下关闭装饰性位移、计数和撒花；不要求所有动效都强制降级为另一种动画。[W3C 交互动效说明](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html)
- 命令面板、暗色模式、额外工作区标签页作为独立后续需求，根据实际使用反馈决定。

验收：记录量不变时无重复动画；大班列表不全屏同时动；启用减少动态效果后数据和操作仍完整可用。

## 5. 推荐开发顺序与检查方法

1. **学生详情作为试点**：收敛样式归属、落实左右区域稳定、统一空/错/加载状态，先解决近期真实发生的问题。
2. **成绩管理与仪表盘**：改善录入与对比，再做与指标有关的图表样式；基础图表、轴、网格、tooltip 统一主题，参考线只使用真实数据或明确设置。
3. **TeachMate**：核对现有过程区和消息操作的真实接入路径，改善更新稳定性、来源定位和教学成果后续动作。
4. **成长森林**：完善状态与单条撤销，再增加一次性阶段变化提示。
5. **回到公共层收敛**：将前三类页面验证过的模式抽为公共组件，避免先做一个没人接入的大型组件库。

每批改造记录“现状截图 → 目标行为 → 涉及文件 → 验收场景”。纯色彩/文案修改不新增同义测试；改变写入、撤销、筛选或任务上下文时复用和补充行为测试。jsdom 用于行为，真实 Safari/WebKit 与 Chromium 页面用于布局、滚动、焦点和绘图核对。不要因为调整内部 DOM 就直接删掉仍然合理的测试约束。

建议的检查样例包括：长学生画像、零分与缺考、不同满分考试、多学科切换、较长聊天、带失败与取消的任务、多班级补录、重复点击撤销。规模可选 50 名学生、1,000 条账本记录、较长会话作为验证样例；这是拟定检查范围，不是已测容量结论。只有观察到实际性能问题，再引入虚拟列表等复杂机制。

实施成果应以任务完成情况衡量：录分时是否需要反复找按钮、画像是否稳定可读、分析出错能否恢复、结论能否找到依据、产物能否直接进入课堂。全屏占满率、动画数量和参考仓库星数不作为验收指标。
