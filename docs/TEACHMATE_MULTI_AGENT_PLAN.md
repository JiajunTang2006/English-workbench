# TeachMate 多 Agent 方案：学生画像与考试分析协同

状态：规划与实现记录  
适用范围：TeachMate 内置 Agent、TeachMate Codex 插件  
核心目标：在确有并行收益时缩短整班分析耗时，同时保持证据、隐私、成本和教师确认边界。

当前实现：Phase 1 已落地（受控任务组、学生独立子运行、预算确认、进度状态、取消、重启恢复和前端 API）；Phase 2 已加入可配置的 `HarnessPool`，通过 `TEACHMATE_HARNESS_POOL_SIZE=2..4` 启用真正的多 Harness 并行。多学生单 Worker 上下文压缩仍保留在后续阶段。

## 1. 结论

TeachMate 值得引入多 Agent，但应采用“按任务图受控编排”，而不是默认让所有请求进入多 Agent。

优先落地两个场景：

1. **整班或多名学生画像**：先共享计算考试事实，再由若干学生诊断 Worker 分批处理，最后统一汇总。
2. **考试分析与学生分析同步执行**：考试整体分析和学生诊断读取同一份冻结数据快照，并行完成后生成一份联合教学简报。

首版不建议“一名学生永久绑定一个 Agent”，也不建议让 Agent 自由创建更多 Agent。主编排器必须预先确定任务数量、作用域、预算和并发上限。

## 2. 为什么这两个场景适合多 Agent

### 2.1 批量学生画像

不同学生之间的个体诊断基本独立，天然适合 fan-out / fan-in：

```text
冻结考试与班级事实
        │
        ├── Worker A：学生 01～05
        ├── Worker B：学生 06～10
        ├── Worker C：学生 11～15
        └── Worker D：学生 16～20
                     │
              汇总与一致性检查
                     │
        逐生画像草稿 + 班级分组建议
```

并行价值来自：

- 学生之间没有必须串行的推理依赖；
- 每个 Worker 可以使用更小、更专注的上下文；
- 单个学生失败时只重试对应分片，不必重跑全班；
- 可逐批展示进度和结果，教师不必等到全班全部完成。

### 2.2 考试分析与学生分析同步执行

两条工作流依赖相同的考试范围，但输出目标不同：

```text
冻结 ExamScopeSnapshot
        │
        ├── Exam Agent：整体分布、难度、共性问题
        └── Student Agents：个体趋势、薄弱项、画像草稿
                     │
              Synthesis Agent
                     │
   考试报告 + 学生画像 + 分层教学行动
```

它能避免教师先等待考试分析、再逐个发起学生诊断，也能把“班级共性问题”和“个体独有问题”放在同一份证据背景中比较。

## 3. 什么时候启用多 Agent

多 Agent 由系统推荐、教师确认，不应仅靠关键词触发。

| 条件 | 默认执行方式 | 原因 |
|---|---|---|
| 单个学生，单个目标 | 单 Agent | 无可并行的独立任务 |
| 2～3 名学生 | 单 Agent 分批/顺序执行 | 编排成本通常高于并行收益 |
| 4～12 名学生 | 2～3 个 Worker | 开始具备明显并行收益 |
| 13～40 名学生 | 3～4 个 Worker，每个处理 4～8 人 | 控制上下文、成本和服务压力 |
| 40 人以上或跨班级 | 后台批处理，按班级建任务组 | 需要断点续跑、预算确认和分班汇总 |
| 同时要求考试分析和 4 名以上学生画像 | Exam Agent + Student Workers 并行 | 两条工作流独立且共享数据快照 |
| 结果必须互相依赖，例如先用考试结论筛人 | 分阶段 DAG | 第二阶段依赖第一阶段，不能假并行 |
| 数据缺失、身份映射不确定或考试范围未冻结 | 禁止启动 | 避免跨范围、错学生和不可审计结论 |
| 预计成本超教师预算或模型并发不可用 | 降级为队列/请求确认 | 并行不是越过预算的理由 |

推荐的价值判断公式：

```text
启用多 Agent = 独立子任务数 ≥ 2
             且预计节省时间 ≥ 30%
             且共享数据已冻结
             且预算已通过
             且运行池有可用并发槽位
```

教师界面不必暴露公式，只展示：“共 32 名学生，建议使用 4 个分析任务并行处理，预计 X 分钟、预算上限 Y 元”。

## 4. 任务拆分原则

### 4.1 不要默认一人一个 Agent

一人一个 Agent 会迅速放大模型请求数、启动成本和限流风险。推荐按学生分片：

- 每个 Worker 默认处理 4～8 名学生；
- 每名学生仍生成独立、可验证的结构化结果；
- 高风险或复杂学生可单独拆成一个 Worker；
- 简单学生由普通批次处理；
- 一个 Worker 的失败不能影响其他分片结果。

### 4.2 先共享计算，再做个体推理

考试统计、班级均值、题目难度、知识点覆盖等确定性事实只计算一次，形成不可变的 `ExamScopeSnapshot`。所有 Worker 只读该快照，禁止各自重复计算班级统计。

每个学生 Worker 只接收：

- 匿名学生 ID；
- 本人考试与历史趋势；
- 与班级基准的必要差值；
- 相关题目、知识点和错误类型证据；
- 当前教师确认画像及其版本号；
- 本次输出 Schema 与预算。

### 4.3 汇总 Agent 只做跨结果综合

汇总阶段不得重新发明事实。它只能引用 Worker 已提交的结构化结果和 evidence ID，用于：

- 识别班级共性与少数个体特例；
- 按共同干预方式对学生分组；
- 生成教师的处理优先级；
- 标记结果冲突、数据不足和需人工核查项。

如果教师只要逐生画像、不需要班级综合，汇总应使用确定性合并器，不再额外调用模型。

## 5. 推荐架构

新增一个受控的 `AnalysisGroup`，其下挂多个现有 `AnalysisRun`：

```text
AnalysisGroup（教师请求与总预算）
  ├─ Snapshot Task（共享事实，必须先完成）
  ├─ AnalysisRun: exam_analysis（可选）
  ├─ AnalysisRun: student_diagnosis shard-01
  ├─ AnalysisRun: student_diagnosis shard-02
  ├─ AnalysisRun: student_diagnosis shard-03
  └─ Synthesis Task（可选，等待所需上游完成）
```

### 5.1 编排器

新增 `MultiAgentPlanner`，只负责生成并校验任务图：

- 解析教师目标和学生范围；
- 决定单 Agent、分片批处理或多工作流 DAG；
- 计算分片、依赖和最大并发数；
- 估算整组 token、费用和时间；
- 生成幂等键，避免重复创建任务；
- 在任何模型调用前冻结作用域和身份映射。

Agent 不能自行越过 Planner 的范围，也不能在运行中扩大学生名单。

### 5.2 运行池

当前 `HarnessManager` 使用一个工作线程串行处理 `session/prompt`。因此真正并行需要引入 `HarnessPool`：

- 首版默认 2 个模型槽位，配置上限 4；
- 每个槽位拥有独立 Harness 进程和会话根目录；
- 同一学生的同一任务不能同时占用两个槽位；
- 遇到模型服务限流时自动降低到 1 个槽位并排队；
- 允许教师取消整组或单个分片；
- 应用重启后从持久化任务图恢复未完成分片。

“并行工具调用”与“多 Agent”要分开：现有 `max_parallel_tools` 只是在一个 Agent 回合里并行读取工具，不能替代多个独立分析 Agent。

### 5.3 建议数据结构

`analysis_groups`

- `id`, `group_type`, `term_id`, `class_id`, `exam_id`
- `status`, `requested_student_count`
- `max_concurrency`, `estimated_cost_yuan`, `actual_cost_yuan`
- `scope_snapshot_id`, `created_by`, `created_at`, `completed_at`

`analysis_group_tasks`

- `group_id`, `analysis_run_id`, `task_role`
- `shard_index`, `depends_on_json`, `status`
- `student_anon_ids_json`, `retry_count`

现有 `AnalysisRun`、`AnalysisEvidence`、`StudentProfileRevision` 保持事实源，不另建一套重复报告模型。

## 6. 两个首版工作流

### 6.1 整班学生画像

1. 教师选择学期、班级、考试和学生范围。
2. 系统校验成绩完整性、历史数据量和当前画像版本。
3. 生成并冻结班级/考试共享快照。
4. Planner 按 4～8 人一组分片，复杂学生可单独分片。
5. Worker 并行生成逐生诊断和画像变更草稿。
6. 每个结果执行 Schema、证据、隐私和版本校验。
7. 已完成分片即时展示；失败分片单独重试。
8. 可选生成班级共性、学生分组和教师跟进顺序。
9. 教师逐条或按“低风险同类项”批量确认画像；系统不得自动写入正式画像。

批量确认也必须满足：每名学生都有独立草稿、独立 evidence IDs 和独立 base version。存在冲突或高风险推断的项目不能批量确认。

### 6.2 一次考试的完整分析

1. 冻结一次考试快照。
2. 并行启动：
   - Exam Agent：整体分布、难度、共性知识点和教学建议；
   - Student Workers：全班或教师选定学生的诊断与画像草稿。
3. Exam Agent 的结果不是 Student Worker 的前置条件；两者都以冻结快照为依据。
4. 两侧完成后运行联合汇总：
   - 哪些问题是全班共性；
   - 哪些学生需要个别干预；
   - 哪些学生可组成同类辅导组；
   - 下周优先处理什么。
5. 输出三类成果：考试报告、逐生画像草稿、班级行动清单。

如果教师要求“先根据考试分析筛出风险学生，再分析这些人”，任务图改为串行两阶段：`Exam Agent → deterministic selector → Student Workers`。

## 7. 一致性、隐私和安全边界

- 所有任务共享同一个 `scope_snapshot_id`，禁止混用后来修改的成绩。
- 跨 Agent 传递匿名 ID，不传姓名、学号或隐私映射表。
- 身份映射只在本地展示层恢复，模型侧始终匿名。
- 每个结论必须引用本任务或共享快照中的 evidence ID。
- AI 只创建 `StudentProfileRevision(draft)`，教师确认后才写入正式画像。
- 使用 `base_version` 做乐观锁；画像已被其他教师更新时，旧草稿必须重新比较，不能覆盖。
- 汇总 Agent 不能访问无关学生的原始细节，只接收完成综合所需的最小字段。
- 取消整组时，已完成结果保留，未开始任务取消，运行中的模型任务按当前运行时能力协作取消。

## 8. 成本和降级策略

批量任务要先估算整组成本，而不是分别触发单次预算门禁。粗略上限可按：

```text
总预算 = 共享快照成本
       + 学生分片数 × 单分片预算
       + 考试分析预算（如有）
       + 汇总预算（如有）
```

优化顺序：

1. 确定性规则和本地统计先行，减少发送给模型的数据。
2. 共享班级事实，禁止每个 Worker 重复拉取。
3. 无跨学生综合需求时不调用汇总 Agent。
4. 超预算时优先减少 Worker 并发只会降低速度，不会降低总 token；真正降本应减少分析范围、缩短输出或仅分析需要更新画像的学生。
5. 服务限流或运行池不可用时自动降级为持久队列，并明确告诉教师“已转为顺序处理”。

## 9. 教师界面

启动前展示：

- 分析范围：考试、班级、学生人数；
- 执行方式：顺序 / 2～4 个任务并行；
- 预计时间和预算上限；
- 将产生的成果；
- 需要教师确认后才写入画像的说明。

运行中展示一个任务组，而不是把多个 Agent 会话散落到侧边栏：

- “共享数据校验完成”；
- “学生画像 18/32 已完成”；
- “考试整体分析已完成”；
- “2 个学生需要核查数据”；
- 支持取消整组、重试失败分片和查看单个学生结果。

完成后按结果而不是按 Agent 展示：考试分析、学生画像、班级行动清单。

## 10. 分阶段落地

### Phase 0：测量基线

- 记录单个学生诊断的耗时、token、费用和失败率；
- 测量 10、20、40 人顺序运行的总耗时；
- 验证模型服务允许的稳定并发数和限流行为。

### Phase 1：批量任务组，但仍可串行执行

- 建立 `AnalysisGroup`、分片、进度、单分片重试和整组预算；
- 共享考试快照；
- 用单 Harness 队列跑通完整闭环；
- 先验证一致性、恢复、取消和画像草稿确认。

### Phase 2：受控并行

- 已引入可配置的 `HarnessPool`（1～4 槽位）；默认仍为 1，设置
  `TEACHMATE_HARNESS_POOL_SIZE=2..4` 后才启用真正的多 Harness 并行，
  每个槽位拥有独立进程、会话根目录和 scope 根目录；
- 当前由运行池提供全局并发上限，单教师并发和 provider 细粒度限流留在灰度阶段补齐；
- 以 10～20 名学生灰度，比较真实耗时和失败率；
- 指标达标后逐步开放到 4 槽位。

### Phase 3：考试分析 + 学生分析 DAG

- 增加工作流依赖和联合汇总；
- 支持全班分析和“先筛选、再诊断”两种模式；
- 输出班级分组干预建议。

### Phase 4：Codex 插件多 Agent 路由

- 在 Skill 中声明何时可以委派学生分片；
- 子 Agent 只调用只读插件工具并返回结构化结果；
- 主 Agent 负责合并，不允许子 Agent 写画像；
- 写入画像仍回到 TeachMate 内置的教师确认流程。

## 11. 发布门禁

满足以下条件后才默认推荐多 Agent：

- 20 名学生任务相对顺序模式的 P50 总耗时至少下降 30%；
- 结构化输出通过率不低于单 Agent 基线；
- 证据引用有效率 100%；
- 学生身份串线为 0；
- 同一快照下重复执行的确定性事实差异为 0；
- 取消、重启恢复、单分片重试均通过；
- 实际总费用不超过教师确认预算；
- 画像正式写入仍保持 100% 教师确认。

若并行只缩短少量时间，却显著增加失败率、限流或费用波动，应保留任务组能力但默认使用队列顺序执行。

## 12. 推荐的首个开发切片

首个切片建议只做“同一考试下 8～12 名学生的批量画像”：

- 2 个 Worker；
- 每个 Worker 4～6 名学生；
- 共享一次考试快照；
- 不做额外汇总 Agent，只做确定性结果合并；
- 所有画像保持待教师确认；
- 支持单分片失败重试和整组取消。

这个切片能最小成本验证多 Agent 的核心价值，也能直接暴露运行池、证据隔离、身份隔离和预算控制是否可靠。验证通过后，再扩展到“考试分析 + 全班学生画像”的完整 DAG。
